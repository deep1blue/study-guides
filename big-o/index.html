Big-O, Ω, Θ: What Complexity Actually Measures

September 28, 2026 · Interview-prep series

Every coding round ends with "what's the complexity?" — and it is not a stopwatch question. This guide goes intuition → mechanism → math: why we count operations instead of seconds, what the three Greek letters actually promise, and how to derive the answer from first principles instead of memorizing it.

1Intuition: growth, not speed

Complexity never measured seconds. It measures elementary operations as a function of input size n. Seconds depend on the machine, the language, the compiler, the day of the week. Operation counts don't. A recipe is "steps per serving"; "how hot your oven runs" is the hardware. Interviewers ask about the recipe.

Why the question matters at all: at small n, everything looks the same. Two Sum on ten elements — brute force and hash map both finish before you blink. At n = 100,000, one takes milliseconds and the other takes minutes. Big-O is the tool that sees that difference before you run the code. It is the interview version of "will this scale" — the same instinct behind scaling laws in ML, just applied to code.

One-line version: Big-O is a claim about how work grows when the input grows. Drop the hardware, drop the constants, keep the shape of the curve.

📄 Deep dive — the canonical reference

  • Cormen, Leiserson, Rivest & Stein, Introduction to Algorithms, 3rd ed., Chapter 3: "Growth of Functions" — §3.1 gives the formal definitions of O, Ω, Θ (the c-and-n₀ machinery); §3.2 catalogs the standard functions and their ordering. This is the source every other explanation is downstream of; if an interviewer ever pushes past the intuition, this chapter is where the answers live.

2The three notations: ceiling, floor, sandwich

Let f(n) be the exact operation count of your algorithm and g(n) a clean benchmark function like n or n². The three letters are three promises about how f relates to g for large n:

Figure 1 — The three promises. O is a ceiling ("at most this bad"), Ω a floor ("at least this much work"), Θ a sandwich ("pinned, up to constants").
  • O (big-O): f(n) = O(g(n)) if f(n) ≤ c·g(n) for all n ≥ n₀, for some constants c, n₀. "Never worse than this."
  • Ω (big-Omega): f(n) = Ω(g(n)) if f(n) ≥ c·g(n) eventually. "At least this much work, no matter the input."
  • Θ (big-Theta): both at once: c₁·g(n) ≤ f(n) ≤ c₂·g(n). The growth rate is pinned, up to constants.

The cultural trap: everyone says "Big-O" when they mean Θ. "Merge sort is O(n log n)" — as a pure ceiling that's weak (O(n²) is also true, and useless); the speaker means the tight bound. When an interviewer asks, give the tight one even if you call it O. Precision is the whole point of the question.

3Deriving the ladder: the math that matters

Three derivations cover ninety percent of interview analysis. Each one earns you a rung of the ladder from first principles.

3.1 Counting pairs: n(n−1)/2 → Θ(n²)

Brute-force Two Sum: for each i, scan every j > i. Comparisons: (n−1) + (n−2) + … + 1 = n(n−1)/2 = ½n² − ½n. The comparisons form a triangle:

Figure 2 — Same problem, two growth curves. Brute force checks a triangle of pairs; the hash-map pass asks one question per element.

Now the entire justification for dropping constants. Divide by n² and take the limit:

n(n−1)/2 ÷ n² → ½  as n → ∞

The ratio settles to a constant, so the shape is n²: Θ(n²). Constants and lower-order terms vanish in the limit. That is the whole reason we drop them — not a convention, a limit argument.

3.2 Halving: where log comes from

While loop: i = n, then n/2, n/4, … until 1. How many halvings to reach 1? For n = 16: 16 → 8 → 4 → 2 → 1 — four steps, and 4 = log₂16. In general, log₂n iterations: O(log n).

The base never matters: logₐn = log₂n / log₂a — a constant factor, and constants die in the limit (see §3.1). Binary search, heap pushes/pops, halving counters: all log n, all base-agnostic.

3.3 The recurrence tree: T(n) = 2T(n/2) + O(n)

4The code: Two Sum, two ways

The canonical problem for this lesson. Same answer, two growth curves — and the diff between them is the entire point:

# Brute force: check every pair. (n-1) + (n-2) + ... + 1 = n(n-1)/2
# -> Theta(n^2) time, O(1) extra space.
def two_sum_bruteforce(nums, target):
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):
            if nums[i] + nums[j] == target:
                return [i, j]

# Hash map: one pass, asking "have I seen target - x?"
# Each dict probe is O(1) average -> Theta(n) time, Theta(n) space.
# The time-memory trade: we BUY the linear pass with linear space.
def two_sum_hashmap(nums, target):
    seen = {}  # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:
            return [seen[need], i]
        seen[x] = i

Notice what changed between the two: not cleverness — a data structure that turns a search into a lookup. That move (search → lookup) recurs across the whole track: L9 (hash maps), L18 (BSTs), L37 (tries).

💻 Deep dive — representative problems

  • Contains Duplicate — same trade in disguise: the set-based solution is Two Sum's hash map with the arithmetic removed.
  • Maximum Subarray — the brute force is Θ(n²); Kadane's is Θ(n). Preview of L8 (subarray patterns).
  • Product of Array Except Self — the follow-up ("do it without division, in O(1) extra space") is exactly the kind of constraint-tightening this track trains for.

5Reading complexity off code

The skill interviewers are actually testing. Five moves:

  • Single loop over n → O(n). Nested loops both running to n → multiply: O(n²). Triangle inner loop (j from i) → n(n−1)/2 → still O(n²) — the triangle never saves you a growth class.
  • Counter halved or doubled each step → O(log n).
  • Sequential blocks → add, keep the max. "O(n) then O(n²)" is O(n²).
  • Independent input sizes → name them: O(n·m), never O(n²).
  • Recursion → write the recurrence, draw the tree, multiply levels × work per level.

And the Python traps — builtins with costs interviewers love to hide inside loops:

6The 6 pitfalls — know the why

1. Loose O instead of tight Θ. Calling a linear scan "O(n²)" is technically true and tells the interviewer nothing. Give the tight bound — that's what the question is asking for.
2. Hidden O(n) inside loops. Slicing, pop(0), string concatenation, max() per iteration — each one quietly turns O(n) into O(n²). The table in §5 is your audit checklist.
3. Average-case amnesia. Dict/set are O(1) average, O(n) worst case. Default to worst-case unless you say otherwise — and always know which one you're quoting. L2 (amortized analysis) unpacks this properly.
4. Log-base pedantry. The base is a constant factor. Don't spend interview breath on it — say "log n" and move on.
5. Forgetting space. The recursion stack counts: naive Fibonacci recursion is O(2ⁿ) time and O(n) space from call depth. Interviewers ask for both; have both ready.
6. n is the size, not the value. "Loop to n" over an integer n is O(n); "loop over the digits of n" is O(log n). Misidentifying n is the fastest way to a wrong answer.

8Self-test

Cover the answers. Say each one aloud until it's clean.

1. Why is wall-clock time a bad measure of algorithm efficiency?

It depends on the machine, language, compiler, and input — none of which are properties of the algorithm. Operation count as a function of n isolates the algorithm's own growth shape, which is what "will this scale" actually asks.

2. Prove n(n−1)/2 is Θ(n²) using limits.

Divide by n²: n(n−1)/2 ÷ n² = (1 − 1/n)/2 → ½ as n → ∞. The ratio converges to a constant, so the function is sandwiched between constant multiples of n² eventually — that's Θ(n²). Constants and lower-order terms vanish in the limit.

3. A loop halves n each iteration, starting from 1024. How many iterations? Complexity class?

10 iterations (1024 → 512 → … → 1 is 2¹⁰). Class: O(log n) — and the base is irrelevant (change-of-base is a constant factor).

4. Your loop does for i in range(n): s += str(i). True complexity, and why?

O(n²). Strings are immutable, so each += copies the whole string-so-far: 1 + 2 + … + n = Θ(n²) character copies. Fix: collect pieces in a list and "".join once → O(n).

5. "Dict lookups are O(1)." What's the asterisk, and what do you assume in an interview?

The asterisk: O(1) average case; worst case (hash collisions, adversarial keys) is O(n). In an interview, quote worst-case unless you explicitly say "amortized/average" — and know which you're quoting.

6. Derive T(n) = 2T(n/2) + O(n) with the recursion tree.

Level 0 does n work; level 1 has two nodes of n/2 (total n); level 2 has four of n/4 (total n); … each level sums to n, and there are log₂n levels before reaching size 1. Total: n·log n = Θ(n log n).

7. "This single linear scan is O(n²)." What's wrong with the statement?

It's a loose upper bound — technically true, informationally empty. The interviewer wants the tight bound: Θ(n). Precision is the point of the question.

8. Why doesn't O(log n) care about the log base?

Change of base: logₐn = log₂n / log₂a. The denominator is a constant, and constants die in the limit (same argument as §3.1). So logₐn = Θ(log₂n) for any base a.

🎯 Your 30-second interview answer

"Big-O is a growth-rate claim about operation count, never a stopwatch. I name n, count the dominant work as a function of n, and drop constants and lower-order terms because at scale the fastest-growing term decides everything. O is the ceiling, Ω the floor, Θ the tight bound — and I give the tight one. Two Sum: brute force makes n(n−1)/2 comparisons, Θ(n²); one hash-map pass probes once per element, Θ(n) time for Θ(n) space. That trade is the whole pattern."
